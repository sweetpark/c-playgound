# P080 · sd35 hcsalt — 취약한 암호화 해쉬함수 하드코드된 솔트 — 호출마다 새 솔트로 치환

## 요구사항

새 계정을 만들 때마다 그 계정 전용 솔트를 발급한다.
- 솔트는 매번 달라야 한다.

이미 `solution.c` 에 **Bad 함수가 들어 있다**(취약점을 먼저 관찰하세요). 같은 소재의 **Good 함수만 구현**한다. 치환 규칙: **호출마다 새 솔트로 치환**.

## 시그니처

```c
unsigned get_salt_bad(void);
int get_salt_good(unsigned *out_salt);
```

## 입출력 예시

| 상황 | Bad 결과 | 이유 |
| :--- | :--- | :--- |
| 계정 100개를 연달아 생성 | **전부 같은 솔트(`0xC0FFEE`)** | SD33의 솔트 방어가 사실상 무효화된다 — 모든 계정이 같은 솔트를 쓰면 그 솔트 하나로 만든 레인보우 테이블이 전체 계정에 통한다 |
| 같은 상황(Good) | 계정마다 다른 솔트 | SD31의 `getrandom` 을 그대로 재사용 |

## 제약

- Bad 함수와 `mock_*` 파일(있다면)은 수정하지 않는다. `solution.c` 의 Good 함수만 채운다.
- Bad 는 **실제로 뚫린다**는 것이 시험의 일부다(자식 프로세스로 실행). Good 은 같은 공격을 막고 정상 입력은 그대로 통과시켜야 한다(과잉 차단 금지).
- 경고 0, ASan/UBSan 0 (`-Wall -Wextra -Werror`).

## 통과 기준

`make P080` → `PASS` (실패 시 `FAIL k` 와 어긋난 항목 출력), 경고 0, ASan/UBSan 0. 힌트: `HINT1.md` → `HINT2.md`.

시험이 확인하는 것:

- Bad는 언제 호출해도 완전히 같은 솔트를 반환해야 한다(레인보우테이블 재사용 가능 = 취약점 재현)
- 첫 번째 호출은 성공해야 한다
- 두 번째 호출도 성공해야 한다
- 세 번째 호출도 성공해야 한다
- Good은 호출마다 매번 새 솔트를 만들어야 한다(세 값이 전부 같을 확률은 무시 가능)
