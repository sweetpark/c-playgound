# NOTE · P104 alog_ring (풀고 난 뒤에 보세요)

**원본 글** (읽기 전용, 여기에 복사하지 않음)
- 「[C] 비동기 로깅과 링 버퍼 — 큐가 가득 차면 어떻게 되나」 — 생산자·소비자, 가득 찼을 때의 정책 세 가지, 종료할 때 비우기
- 「[C] 배열 기반 원형 큐(Ring Buffer)」 — `front`/`back` 으로 만드는 큐 (이 문제의 큐는 `head` + `count` 로 같은 일을 한다)

**함정 요약**
- `write` 안에서 큐가 찰 때까지 `cond_wait` — 서비스 스레드가 로그 때문에 멈춘다. 이 문제의 핵심은 "기다리지 않는다"
- 줄을 **포인터만** 저장 — 호출자가 버퍼를 바꾸는 순간 로그 내용이 바뀐다
- sink 를 **락을 쥔 채** 호출 — sink 가 느린 동안 모든 `write` 가 같이 막힌다 (큐가 찼다기보다 락 때문에 멈춘 것처럼 보인다)
- `destroy` 가 `stop` 만 세우고 join 하지 않음 / join 하더라도 남은 줄을 안 내보내고 끝냄 — **종료 직전의 로그가 사라진다.** 장애 원인은 보통 마지막 몇 줄에 있다
- FULL 을 `count == cap` 일 때만 켜고, 한 칸만 비어도 바로 끔 — 경계에서 상태가 계속 뒤집힌다 (히스테리시스가 없다)
- 소비 스레드가 `count == 0` 일 때 바쁜 대기(busy-wait) — 로그가 없는 동안에도 CPU 를 쓴다. 조건변수로 잔다
- `stop` 을 본 순간 바로 종료 — 큐에 남은 줄이 버려진다. "비었고 stop" 일 때만 끝낸다
- 통계 카운터를 락 없이 증가 — 여러 생산자가 있으면 `enq + dropped` 가 실제 호출 수와 어긋난다

**한 줄 설명 연습**: "느린 소비자 + 한정 큐 + 기다리지 않는 생산자 = 로그 유실이 *설계된 동작*이다" 를 내 말로 쓴다. 그리고 유실을 *알아채는* 방법(통계, FULL 상태)이 왜 꼭 필요한지도.
