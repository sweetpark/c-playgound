# NOTE · P110 wal_kv (풀고 난 뒤에 보세요)

**원본 글**: 「[DB] 인메모리 DB의 내구성 — 체크포인트와 로그 복구」

**함정 요약**
- 메모리를 먼저 바꾸고 로그를 나중에 씀 — 사이에서 죽으면 클라이언트에는 "성공"이라고 했는데 흔적이 없다
- `fflush` 만 하고 `fsync` 를 안 함 — `fflush` 는 C 라이브러리 버퍼를 OS 로 보낼 뿐이다. 전원이 나가면 OS 캐시는 사라진다 (프로세스만 죽는 경우에는 OS 에 있으니 안전)
- 찢어진 꼬리를 **재생에서만 무시**하고 파일에서는 안 자름 — 다음 기록이 반쪽 줄 뒤에 붙어 한 줄로 합쳐지고, 다음 복구 때 둘 다 버려진다 (`[7]`)
- crc 가 틀린 줄을 **건너뛰고** 뒤를 계속 재생 — 중간이 깨졌다면 뒤의 기록은 그 앞 상태를 전제로 한 것이라 믿을 수 없다 (`[8]`)
- 옛 기록(`lsn <=`)을 이상한 기록으로 보고 멈춤 — 체크포인트 직후 크래시 뒤에 새 기록이 이어졌다면 새 기록까지 잃는다 (`[6]`)
- 줄바꿈 없는 마지막 줄을 crc 가 맞는다는 이유로 받아들임 — 끝까지 쓰였는지 알 수 없다. 형식의 일부(줄바꿈)까지 확인한다 (`[7b]`)
- END 줄 없는 스냅샷을 그대로 읽음 — 쓰다 만 스냅샷이 정식 데이터가 된다 (`[11]`)

**시험이 검사하지 못하는 두 규칙 (그래도 중요하다)**
1. 스냅샷을 **정식 이름에 바로** 쓰면, 쓰는 도중 죽을 때 반쯤 쓴 스냅샷이 남는다. 임시 파일 + `rename`(같은 파일시스템에서 원자적)이 답이다.
2. 로그를 **스냅샷보다 먼저** 비우면, 그 사이에 죽을 때 로그도 스냅샷도 없다. 스냅샷이 완전히 자리 잡은 **뒤에** 비운다. 더 엄밀하게는 `rename` 뒤에 디렉터리도 `fsync` 해야 이름 변경이 디스크에 닿는다.
시험은 프로세스를 중간에 끊을 수 없어서 이 두 가지를 눈으로 검토해야 한다.

**이 문제의 단순화**: 키 수만큼 선형 탐색(느림), 체크포인트 동안 쓰기 금지, 로그 크기 상한 없음, 그룹 커밋 없음. 실제 DB 는 이걸 해결하는 데 대부분의 복잡도를 쓴다.

**한 줄 설명 연습**: "변경을 로그에 먼저 남기고(WAL) 가끔 스냅샷을 찍으면, 크래시 후 스냅샷에 로그를 되감아 복구한다. 깨진 로그 꼬리는 버리고 파일에서도 잘라낸다." 를 내 말로 쓴다.
